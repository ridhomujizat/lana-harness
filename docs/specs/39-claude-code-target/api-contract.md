## Revision 3 (2026-11-08): one-click sign-in (REQ-CCT-012)

All endpoints are behind the dashboard session and CSRF check (owner only). `{name}` is a Claude Code
account: `claude-code` (built in) or a `[providers.<name>]` table of kind `claude-code`; another name
answers 404. A sign-in state is `{"state":"idle|running|succeeded|failed|cancelled","error":"<URL-stripped
line, failed only>","started_at":"<RFC 3339>|null","finished_at":"<RFC 3339>|null"}`; it lives in memory only.

| Operation ID | Change | Requirements |
|---|---|---|
| `API-CCT-015` | `POST /v1/router/claude-code/accounts` body `{"name"?: string}` (empty body allowed): writes `[providers.<name>] kind = "claude-code"` (name default `claude-2`, `claude-3`, … first free provider name), creates `$LANA_HOME/claude/<name>` (0700), starts the sign-in, answers **202** `{"name","config_dir","version","restart_required","login_command","sign_in":{"state":"running",…}}`. 409 `exists` for a taken name, 409 `builtin` for `claude-code`, 409 `config_missing`, 422 for a bad name. | REQ-CCT-012 |
| `API-CCT-016` | `POST /v1/router/claude-code/accounts/{name}/sign-in` → **202** state (`running`), **409** `sign_in_running` while one runs. `GET …/sign-in` → 200 state. `DELETE …/sign-in` → 200 state after cancelling (process group stopped). The daemon runs `claude auth login` with the account env, stdin closed, stdout discarded, 10-minute deadline; success is exit 0. The built-in account signs in to the owner's own `~/.claude`. | REQ-CCT-012 |
| `API-CCT-017` | `POST /v1/router/claude-code/accounts/{name}/sign-out` body `{"confirm"?: bool}` runs `claude auth logout` (30 s) and answers 200 with the refreshed account row (as in `accounts[]` below). The built-in account needs `{"confirm": true}`, else **400** `confirm_required`. 409 `sign_in_running`; 422 `sign_out_failed` with the URL-stripped line. | REQ-CCT-012 |
| `API-CCT-018` | `DELETE /v1/providers/{name}?remove_folder=1` for a Claude Code account: the in-use 409 rules first, then the folder check (**409** `folder_outside_home` unless the folder lies inside `$LANA_HOME/claude/`; nothing is changed), then sign-out (a failure is reported in `message`, not fatal), then the folder is deleted, then the table. The answer adds `"folder_removed": true`. Without the flag the folder stays as before. Other values than `1`/`0`/`true`/`false` answer 400. | REQ-CCT-012 |
| `API-CCT-019` | `PUT /v1/router/claude-code/accounts/{name}/label` body `{"label": string, "expected_version"?: string}` stores `label` in the account table (trimmed, one line, at most 60 characters; `""` removes it) and answers `{"name","label","version","restart_required"}`. The built-in account answers 409 `builtin`. Config: `[providers.<name>] label` is accepted for kind `claude-code` only. `GET /v1/providers` rows of kind `claude-code` add `label`. | REQ-CCT-012 |
| `API-CCT-020` | `GET /v1/router/claude-agent` `accounts[]` items add `label` (stored label or `""`), `display_name` (label, else e-mail, else name), and `sign_in` (the state above; `idle` when none). `login_command` becomes `CLAUDE_CONFIG_DIR='<dir>' CLAUDE_SECURESTORAGE_CONFIG_DIR='<dir>' claude auth login` (`claude auth login` for the built-in account). | REQ-CCT-012 |
| `API-CCT-021` | Process environment of every `claude` run for a named account (turns, `auth status`, test turns, `auth login`/`logout`): `CLAUDE_CONFIG_DIR` and `CLAUDE_SECURESTORAGE_CONFIG_DIR` = the folder (each once), without `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`. The built-in account keeps the daemon's folder variables. | REQ-CCT-012 |

## Revision 4 (2026-11-08): usage probe (owner request)

The owner: the Claude Code plan windows on Quota and Usage did not refresh. Before this revision they
moved only with the `rate_limit_event` of a turn. All endpoints are behind the dashboard session and,
for `POST`, the CSRF check.

| Operation ID | Change | Requirements |
|---|---|---|
| `API-CCT-022` | **Usage probe.** For one account lana runs `claude -p /usage --output-format stream-json --verbose --no-session-persistence --setting-sources project` with the account environment (`API-CCT-021`), stdin closed, in a new empty temp folder (removed afterwards), its own process group, a 45 s deadline (process group stopped on timeout). `/usage` is a local command: no model call. `--setting-sources project` in the empty folder skips the owner's user settings, so no hook or plugin runs; `--bare` is not used because it never reads the OAuth login. The probe fails when the result has `is_error`, reports any `input_tokens` or `output_tokens` > 0, or has no result line. An `api_key` account is no subscription and runs nothing. | REQ-CCT-011 |
| `API-CCT-023` | **Parsing.** From the result text (else the assistant text): `Current session: N% used · resets <when>` → window `five_hour`; `Current week (all models): …` → `seven_day`; `Current week (<Model>): …` → `seven_day_<model lowercased, each run of non-alphanumerics → _>` with `label` `"Weekly · <Model>"`. `utilization` = N/100, `status` `allowed` (or `rejected` at 100 %). `<when>` is `<Mon> <D> at <h[:mm]>am/pm (<IANA zone>)` read in that zone (year: the next occurrence at or after now − 1 day), `in 2h 5m`, or absent (no `resets_at`). Text without plan lines that says it is not a subscription (API usage, Console) gives no windows and the snapshot error `Not a subscription: …`; "not logged in" or an unknown form is a probe error. | REQ-CCT-011 |
| `API-CCT-024` | **Refresh.** `GET /v1/router/limits?refresh=1` and the new `POST /v1/router/limits/refresh` (same answer as `GET /v1/router/limits`) fetch the API providers' balances (5 min throttle, as before) and, in parallel, run the probe for the built-in account (when `claude` is found) and every Claude Code account that is not `disabled` and not `auth = "api_key"`, at most once per 60 s per account; a throttled account keeps its snapshot and `updated_at`. Windows merge into the account's snapshot by `type` (other windows and a stored `label` stay); a failed probe sets the snapshot `error` and keeps the old windows and `updated_at`. A later turn's windows also merge and clear the error. | REQ-CCT-011 |
| `API-CCT-025` | **Window fields.** `windows[]` items of `GET /v1/router/limits` and of `GET /v1/router/claude-agent` `accounts[]` add `label` (omitted when empty) and `source`: `"stream"` (a turn's `rate_limit_event`) or `"usage_probe"`. | REQ-CCT-011 |
| `API-CCT-026` | **UI.** Quota (top right), Usage (next to the range picker; also reloads the usage), and the Claude Code page (Accounts header) show **Refresh** with a spinner and "Updated <relative time>". On mount each of them refreshes once when a Claude Code snapshot is older than 5 minutes (or a signed-in account has none); the 60 s daemon throttle stops loops. Extra weekly windows show under the account by their label ("Weekly · Fable"); the probe error shows inline. | REQ-CCT-009, 011 |

## Revision 5 (2026-11-08): built-in account settings, guardian calls

Bug fixes found in use. (Revision 4 is the usage probe above.)

| Operation ID | Change | Requirements |
|---|---|---|
| `API-CCT-027` | Amends API-CCT-001 and API-CCT-010. An optional `[providers.claude-code]` table with `kind = "claude-code"` holds **only** the built-in account's settings: `allow_scheduled`, `disabled`, `binary`, `auth`, `api_key_env`. `config_dir` and `label` are refused ("not allowed for the built-in account: it always uses your normal Claude Code login"); a `[providers.claude-code]` table of another kind is still refused ("claude-code is built in"). The table is not a configured provider: it is not listed as one, a legacy `provider = "claude-code"` key stays unknown, and `claude-code/*` addresses stay Claude Code addresses. The router reads it as the built-in account's config: `allow_scheduled` lets scheduled runs (calendar, workflow nodes) use it (REQ-CCT-008, REQ-CCT-010); `disabled = true` fails its targets before output, so the chain falls back (API-RTR-001 revision 2); `binary`, `auth`, `api_key_env` win over an agent's legacy keys and the first agent's binary. `PUT /v1/providers/claude-code` with `kind: "claude-code"` writes that table (an absent key keeps its stored value), creates no folder, and answers `login_command: "claude auth login"` with no `config_dir`; `config_dir` in the body answers 422 on `providers.claude-code.config_dir`; another kind answers 422 "claude-code is built in". `DELETE /v1/providers/claude-code` stays 409 `builtin`. `GET /v1/providers` lists the built-in row once (`builtin: true`) with the stored `allow_scheduled` and `disabled`. The UI request shape is unchanged. | REQ-CCT-008, REQ-CCT-010 |
| `API-CCT-028` | A workflow guardian's structured calls (spec 33: Workflow assistant graph edits, API-WF-017; failure decisions, REQ-WF-008) are lana background work. They run as a lana-loop turn on the guardian's **background chain** (`llmcall.AgentBackgroundChain`: the agent's chain without its Claude Code targets, else `[router] background_model`, REQ-CCT-007), never in Claude Code, whatever `allow_scheduled` says. The Workflow assistant is such a structured call (its reply is a JSON graph proposal), not a conversational agent turn. Without a background chain the call fails before it starts; the assistant answers **503** `guardian_needs_background_model` with the message "The guardian <agent> runs on Claude Code. Set a background model in Router (or add an API model to its combo) so it can plan workflow changes." (other guardian failures stay 503 `guardian_unavailable`), and a failure decision fails with the same text in the run log. Workflow agent, bot, and worker nodes are the owner's agent work and keep REQ-CCT-008: they run in Claude Code when the account (or agent) sets `allow_scheduled`, else on the chain's other targets, else they fail. | REQ-CCT-007, REQ-CCT-008 |
